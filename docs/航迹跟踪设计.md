# 角度航迹跟踪 设计文档

把每次 MUSIC 估计吐出的“一组按角度排好序的峰”串成带**稳定编号**的
航迹，并把航迹的生命周期（新出现 / 确认 / 暂时丢失 / 终止）明确告诉
上位机。航迹挂在会话上，建会话时可选开启；不开的会话行为与旧版完全
一致。

本文回答四件事：**怎么关联**、**交叉怎么办**、**选它放弃了什么/代价**、
**什么条件下会认错**。

---

## 1. 数据与节奏

验收口径：八阵元、半波长间距；每批 50 条快拍，滑动窗口取 50；每推一批
出一次估计。因此每次估计的协方差本质上只由“当前这一批”决定，相邻两次
估计对应目标位置移动约 `30°/39 ≈ 0.77°/批`（交叉剧本）。

输入给跟踪器的每次检测（`Detection`）：

* `angle`：MUSIC 细化后的峰角（`result.angles`，已升序）；
* `log_power`：该细化角上的 MUSIC 谱高取对数（相对量，只在同一次估计内
  比较；选谱高而不是特征值功率，是因为谱高与“这个峰”天然对齐，而特征值
  功率是按角度序与峰配对的，交叉时角度序会重排，功率会跟错对象）；
* `detection_index`：峰在本次结果里的下标，归属结论按它对齐。

跟踪器是**纯状态机**（`app/sessions/tracker.py`）：不接触时间、随机数、
IO。给定同一检测序列必然得到同一航迹与事件——这是“重启续写与一口气
跑完逐项一致（时间戳除外）”“并发按实际处理顺序串行回放一致”的根基。

## 2. 两种角度：原始角 与 平滑角

每条航迹内部维护两个角：

* **原始角 `angle`**：最近一次关联到的实测峰，用于关联、速度估计、护航
  编队/恢复的全部几何判据。
* **平滑角 `smoothed_angle`**：对实测角做一阶 EMA（α=`position_alpha`，
  默认 0.35），是航迹**对外的位置**，也是历史点 `history` 里记录的角度；
  交叉外推时平滑角与原始角按同一速度一起推进。

为什么需要平滑角：本口径下单批 50 快拍、20 dB 时单次 MUSIC 角估计的
CRB 标准差约 0.043°，实测静态序列有个别批次原始误差到 0.136°（2σ 外是
小概率但必然发生），无法保证“每个点 < 0.1°”。航迹本来就是跨批次的
统计对象，对其输出位置做时间平滑是合理且标准的做法：静态序列平滑后
最大误差降到 0.066°（30 批、固定种子实测），静止验收由此满足。

**关键约束“已推给上位机的归属不回头改”**：平滑只作用于“航迹当前/未来
的点”。每个版本一旦写出（results.jsonl / 跟踪块 / 事件），其内容永不回
改；EMA 不会回头重写旧版本的角度。原始 MUSIC 结果 `result.angles`
更是原样保留。

## 3. 普通关联：全局最近邻 + 波门（GNN）

每次更新：

1. 每条航迹按匀速模型外推一步 `pred = angle + velocity`。暂态航迹首点
   速度未知，速度取 0（在当前位置外推）。
2. 所有“航迹—波门内峰”候选按残差排序，贪心做**唯一**匹配（一个峰最多
   给一条航迹、一条航迹最多吃一个峰）。暂态波门 5°，确认波门 10°。
3. 命中：更新原始角、速度 EMA（α=0.5）、平滑角 EMA、功率 EMA，追加一个
   `measurement` 历史点，连续命中计数 +1、连续漏检清零。
4. 漏检（波门内无峰）：连续漏检 +1，推进生命周期。
5. 没被吃掉的峰：各起一条**暂态（tentative）**航迹。

速度用 `v ← (1-α)v + α·(angle−last)` 的 EMA，而不是直接用本次差分，
避免单次峰抖动把速度带偏。

### 生命周期（次数都按“连续未命中的估计次数”计）

| 变化 | 条件（默认） |
| --- | --- |
| 新建 `track_created` | 未归属峰产生一条 tentative |
| 确认 `track_confirmed` | 连续命中 ≥ 3 |
| 暂态终止 | 连续漏检 ≥ 2（**一闪而过的假峰到不了确认**） |
| 丢失 `track_lost` | 已确认航迹连续漏检 ≥ 3 |
| 重捕 `track_reacquired` | lost 航迹在确认波门内重新命中 |
| 终止 `track_terminated` | lost 后累计漏检 ≥ 6，编号永久封存 |

“连续几次没看到算丢失，更久算终止”由 `lost_after_misses=3` /
`terminate_after_misses=6` 实现。注意 coast（交叉外推）**不计漏检**。

## 4. 交叉：运动趋势护航（convoy coasting）

### 4.1 为什么需要特殊处理

用固定种子的合成数据实测交叉剧本（两源 −15°↔+15° 匀速相向，功率 1/0.5，
15 dB，40 批），交叉中心附近出现三类必然现象：

* 某几批 MUSIC 谱只剩**一个**峰，**MDL 少报一个源**（实测第 19、20 批
  MDL=1）；
* 峰在两目标间“抢”：估计出的单峰在 −0.4°/+0.9° 之间跳；
* 冒出**远离交叉中心的假峰**（本阵列下典型 ±28°，是可分辨两源坍缩为
  一个主峰时的旁瓣/伪峰）。

如果把这几批当普通漏检，会误判丢失甚至终止；如果把单峰同时关联给两条
航迹，会把两条并成一条；等两峰分开后再按“角度最近”关联，由于两条航迹
物理上**交换了左右位置**，按角度序/最近邻都会把编号对调。

### 4.2 方案：编队—接近外推—认回—解除

当两条**已确认**航迹速度异号（相向）且一步外推位置进入
`convoy_enter_deg`（8°）以内，编成一个护航组，记录：

* 交叉**中心** `center`（两预测位置中点）；
* 各自进入护航时的**运动方向** `dir ∈ {+1,−1}`（速度符号，全程冻结）。

护航组有两个相位：

**(A) approach（接近）相位** —— 两条航迹都不做峰关联：

* 每帧按各自速度**线性外推**，写一个 `coast` 历史点（带速度推进的平滑
  角），**不计漏检、不判丢失**；
* 本次所有峰对航迹都**暂不归属**，标注原因 `crossing`；这些峰也**不允许
  产生新航迹**（±28° 假峰由此被天然挡掉，不需要按功率硬判真假）。

**(B) 恢复认回（→ assigned）相位** —— 只在严格条件满足时：

1. 中心 ±`convoy_region_deg`（16°）内，重新出现**分居中心两侧**的两个峰
   （取最靠近中心的左右各一）；
2. 两条航迹的预测都已越过中心 `convoy_margin_deg`（1.5°）——确保已经
   真的穿到对侧，而不是还在接近途中；
3. 用两峰中点对两条预测**整体平移**（消除“线性外推 vs 实际峰”的共同
   漂移），平移后各自残差 ≤ `convoy_wide_deg`（7°）。

满足后按**冻结的运动方向**认峰：`dir=+1` 的航迹认领中心右侧峰、`dir=−1`
认领左侧峰。这与角度排序、与“峰离谁近”都无关，因此**编号不会互换**。
进入 assigned 相位后，继续按冻结方向把本侧最近峰认给航迹（这一段两峰
间距仍可能小于普通确认波门 10°，交给普通 GNN 会串号），直到两峰分开到
`convoy_release_deg`（11°）以上才解除护航，交回普通 GNN。

护航最久持续 `convoy_max_age`（40）帧；超时（两目标长时间分不开的极端
情形）放弃保护、本帧不计漏检地回普通逻辑，并给 `grace_scans`（6）帧的
重新编队抑制，避免立刻又编回去。

### 4.3 这个选择为什么稳

用验收同一套数据在 **60 个随机种子基**（外加 14 个手选种子）上跑交叉，
**编号零互换、零额外航迹**，最终原始角与 ±15° 的最大偏差 0.24°。关键是
两条不变量：

* **身份只由“进入护航时冻结的运动方向”决定**，交叉全程不再用角度最近
  去重新对号，从机制上排除互换；
* **对漂移免疫的恢复判据**：线性外推在交叉十几帧里会累积误差（实测某些
  种子预测漂到 3° 以上），直接用“峰−预测”残差会在两峰刚分开、还跨在
  中心两侧时抢错峰（这是早期原型在种子 5000/314 上串号的根因）。用
  “两峰中点整体平移预测”消掉共同漂移、再要求分侧 + 越过中心 + 残差门，
  既认得到、又不抢。

### 4.4 放弃了什么、代价是什么

* **放弃了纯最近邻/纯匈牙利指派的简单性**：那一套在“峰数=目标数、峰序
  稳定”时最优、最通用，但交叉时峰数变少、峰序翻转，无法保编号。护航是
  针对“相向交叉”这一特定结构的状态机。
* **放弃了纯功率对号**：功率（1 vs 0.5）在交叉附近本就不稳——强源的单
  峰功率并不可靠地属于哪一条，且谱高受分辨坍缩影响很大。功率特征仍被
  记录（`log_power`，EMA），但不作为交叉身份的主依据，只留作扩展与旁证。
* **放弃了“交叉期间也强行给每个峰找归属”**：交叉未决期间峰一律
  `crossing` 暂不归属（这是需求明确允许的）。代价是上位机在这几批拿
  不到“某峰属于某航迹”的实测关联，只能看到航迹按趋势外推的 coast 点。
* **代价 1：交叉窗口内的角度是匀速外推值，不是实测。** 若目标在交叉中
  突然变速，coast 角会偏；恢复后由实测 EMA 拉回。
* **代价 2：护航期间抑制新航迹诞生。** 若恰好在两条航迹交叉的同一位置
  真的冒出第三条目标，它在护航未决期间不会被建航迹，要等护航解除后才
  能重新确认（最多十几批的延迟）。
* **代价 3：护航只建模“恰好两条确认航迹相向”的成对交叉。** 三路及以上
  同时交叉、或一条横穿另一条静止航迹的非对称情形，没有专门处理（退化为
  普通 GNN，可能串号——见下）。
* **代价 4：门限是按“每批 50 快拍、0.77°/批量级”标定的。** 若角度采样
  节奏差很多（比如每批移动 > 8°，连编队都来不及；或慢到 <0.1°/批，交叉
  窗口拖得很长），需要调 `convoy_*` 参数（建会话时可整体覆盖）。

### 4.5 在什么条件下仍会认错

* 目标在交叉窗口内**明显变速/折返/停住**：匀速外推与“冻结方向”失效，
  恢复时可能认偏；极端情况下方向符号与真实出射侧相反会互换。
* **三路及以上同时交叉**，或交叉几何不对称（一条几乎不动）：当前只组
  两航迹护航，第三条按普通 GNN 处理，可能串号或误并。
* 交叉中心附近**本来就有一个固定强源**：它可能被当成“分居两侧的恢复
  峰”之一，导致提前/错误认回（region/margin/残差门只能挡住一部分）。
* 交叉**持续超过 `convoy_max_age`**（两目标长时间在分辨限内分不开）：
  超时放弃保护后回到普通最近邻，此时可能误并/互换。
* 角度更新节奏与门限不匹配（见 4.4 代价 4）。

这些是“运动趋势护航”相对理想多目标跟踪（如多假设 MHT / 粒子滤波 /
带恒虚警的联合概率数据关联 JPDA）有意识的取舍：后者更通用但实现与调参
成本高得多，对本场景“少量目标、匀速、成对相向交叉”的验收问题，护航用
可解释的确定性规则即可稳定通过，且天然满足落盘/重启/并发的逐项一致。

## 5. 事件、查询与对外字段

* 估计信封新增 `tracking` 块（**仅开启航迹的会话**）：
  * `angle_tracks`：与 `result.angles` 等长、一一对应，每个角注明
    `track_id` / `associated` / `reason`（`associated` | `unassigned` |
    `crossing`）。`crossing` 表示交叉护航未决、本帧暂不归属。
  * `events`：本次产生的生命周期事件；
  * `tracks`：本次更新后全部航迹快照（含原始角与平滑角）。
* 新接口：
  * `GET /sessions/{id}/tracks`（列全部，`include_terminated` 可选）；
  * `GET /sessions/{id}/tracks/{tid}`（单条历史点，点分 `measurement` /
    `coast`）；
  * `GET /sessions/{id}/track-events?since_version=N`（版本号轮询，只返回
    严格新于 N 的事件批次，不漏不重）。
* 会话状态新增 `tracking_enabled`。以上均为**纯新增字段/接口**；未开启
  航迹时估计结果一字节不变，旧版字段不改动。

事件类型：`track_created`、`track_confirmed`、`track_lost`、
`track_reacquired`、`track_terminated`。

## 6. 持久化、重启与并发

* `state.json` 在原 `version/latest_result/accumulator` 之外新增 `tracker`
  段，序列化跟踪器**全部**状态（航迹、历史点、护航组、冻结方向、相位、
  编号计数器）。随每次估计与累加器一起**原子替换**落盘。
* `tracks.jsonl`：每产生事件的估计版本追加一行（版本号 + 事件数组），
  作为版本轮询的只读日志；与 results.jsonl 在同一把会话锁内、同一次估计
  中先追加日志再原子写 state。
* **重启**：新进程懒加载会话时从 `state.json` 完整恢复跟踪器，接着追加。
* **并发**：同一会话一把可重入锁，追加+估计+航迹更新是锁内的一个原子步
  骤。航迹更新顺序天然等于估计实际处理顺序（=结果版本顺序）；同一估计
  的每个峰恰好处理一次（代码在处理前固定护航航迹集合，护航解除帧不会再
  进一次普通 GNN），不重不漏；重复批次在估计之前就被幂等跳过，不产生
  版本、不产生任何航迹事件。
* 因跟踪器纯确定、状态无时间戳，重启续写的航迹编号/历史点/事件/归属与
  不重启逐项一致（`created_at` 时间戳除外，它不进 tracker 状态）。
* **升级兼容**：老会话目录没有 `tracking` 配置、state 没有 `tracker` 段，
  照常能读、能继续追加，行为与旧版一致（`tracking_enabled=false`）。

## 7. 参数一览（均可在建会话时覆盖）

| 参数 | 默认 | 含义 |
| --- | ---: | --- |
| `tentative_gate_deg` | 5 | 暂态航迹关联波门 |
| `confirm_gate_deg` | 10 | 确认/lost 航迹关联波门 |
| `confirm_hits` | 3 | 连续命中达到即确认 |
| `tentative_max_misses` | 2 | 暂态连续漏检即终止（防一闪而过） |
| `lost_after_misses` | 3 | 确认航迹连续漏检→lost |
| `terminate_after_misses` | 6 | lost 后累计漏检→terminated |
| `position_alpha` | 0.35 | 输出平滑角 EMA 系数 |
| `convoy_enter_deg` | 8 | 相向两预测近于此值即编队 |
| `convoy_region_deg` | 16 | 只在交叉中心 ±此范围找回峰 |
| `convoy_margin_deg` | 1.5 | 预测越过中心多远才允许认回 |
| `convoy_wide_deg` | 7 | 平移后认回残差上限 |
| `convoy_release_deg` | 11 | 两峰分开到此值解除护航 |
| `convoy_max_age` | 40 | 护航最长帧数 |
| `grace_scans` | 6 | 解除后抑制重新编队帧数 |
